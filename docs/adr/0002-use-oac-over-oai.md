# ADR 0002: S3 へのアクセス制御に OAI ではなく OAC を採用する

## ステータス

承認済み（2026-08）

## 背景

CloudFront から S3 へアクセスさせる際、S3 バケットを公開せずに配信する必要がある。
バケットを公開すると CloudFront を迂回した直接アクセスが可能になり、
WAF による保護もキャッシュも効かなくなるためである。

## 検討した選択肢

**S3 静的ウェブサイトホスティング** — バケットを公開して配信する最も簡単な方法。
ただし直接アクセスを防げず、HTTPS も自前で用意する必要がある。

**Origin Access Identity (OAI)** — CloudFront 専用の特殊なユーザーを作成し、
バケットポリシーでそのユーザーのみを許可する従来方式。

**Origin Access Control (OAC)** — CloudFront から S3 へのリクエストに
SigV4 署名を付与し、バケットポリシー側で SourceArn 条件により検証する現行方式。

## 決定

**OAC を採用する。**

## 理由

OAI は AWS が後継として OAC を推奨しており、新規構築で選ぶ理由がない。

技術的にも OAC が優れている。OAI は SSE-KMS で暗号化されたオブジェクトに
対応できないが、OAC は対応する。また署名ベースであるため、
バケットポリシーの条件に `AWS:SourceArn` を指定でき、
特定のディストリビューションのみに限定できる。

この条件指定は重要で、これがないと世界中のあらゆる CloudFront
ディストリビューションから当該バケットを読めてしまう。

## 実装上の課題

バケットポリシーは CloudFront の ARN を必要とし、CloudFront は S3 を必要とするため、
モジュール間で循環参照が発生する。

これを避けるため、`cdn` モジュールへ渡す S3 のドメイン名は
`module.static_site` の output ではなくバケット名から文字列で組み立て、
`static_site` へ渡す ARN はアカウント ID とディストリビューション ID から
`locals` で構築する形とした。

## 結果

- S3 バケットはパブリックアクセスを全ブロックした状態で運用
- CloudFront 経由以外のアクセス経路が存在しない
- バケットポリシーの許可アクションは `s3:GetObject` のみ
