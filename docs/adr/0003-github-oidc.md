# ADR 0003: GitHub Actions の AWS 認証に OIDC を採用する

## ステータス

承認済み（2026-08）

## 背景

GitHub Actions から S3 へのファイル同期と CloudFront のキャッシュ削除を行うため、
AWS の認証情報が必要になる。

## 検討した選択肢

**IAM ユーザーのアクセスキーを GitHub Secrets に保存** — 最も一般的な方法。
設定が簡単で参考資料も多い。ただし長期有効な認証情報がリポジトリ設定に
保存され続けることになる。

**OIDC による一時認証** — GitHub が発行する短命な ID トークンを AWS が検証し、
`sts:AssumeRoleWithWebIdentity` により一時的な認証情報を発行する方式。

## 決定

**OIDC を採用する。**

## 理由

アクセスキー方式は、鍵そのものが存在し続けることが根本的な弱点である。
ローテーションを怠れば無期限に有効であり、誤ってログや設定ファイルへ
出力されれば即座に悪用され得る。

実際、本プロジェクトの構築過程でローカル環境のアクセスキーを
誤って外部へ露出させる事象が発生した（該当キーは即時無効化済み）。
長期認証情報を持つこと自体がリスクであることを実体験として認識している。

OIDC ではキーが存在しない。実行のたびに一時的な認証情報が発行され、
セッション終了後は失効する。漏洩し得る対象そのものを排除できる。

## 実装上の要点

**信頼ポリシーの条件指定が最重要である。**

    "token.actions.githubusercontent.com:sub": "repo:sudo-taichi@317182855/portfolio@1334778771:ref:refs/heads/main"

リポジトリとブランチの両方を限定している。これを `repo:*` のように
緩く設定すると、第三者のリポジトリからロールを引き受けられてしまう。
OIDC 設定における最も典型的な事故要因である。

`aud` 条件によりトークンの受け取り先が AWS STS であることも検証している。

ワークフロー側では `permissions: id-token: write` が必須で、
これを忘れるとトークンを取得できない。`contents` は `read` に絞っている。
## 遭遇した問題と原因

初回設定時、信頼ポリシーの条件を以下のように記述したが認証が通らなかった。

    repo:sudo-taichi/portfolio:ref:refs/heads/main

CloudTrail の `AssumeRoleWithWebIdentity` イベントを確認したところ、
実際に送られていた `sub` クレームは以下だった。

    repo:sudo-taichi@317182855/portfolio@1334778771:ref:refs/heads/main

ユーザー名とリポジトリ名の後ろに、それぞれの不変 ID が付与されている。
これはアカウント名やリポジトリ名の変更による権限の乗っ取りを防ぐための仕様である。

多くの解説記事は ID なしの形式を前提としているため、
ドキュメントを参照するだけでは気づけない。
切り分けとして条件を一時的に `repo:*` へ緩めて疎通を確認し、
CloudTrail から実際の値を取得して正しい条件を特定した。

**教訓:** OIDC の信頼ポリシーが通らない場合、推測で修正を繰り返すより
CloudTrail で実際のクレーム値を確認する方が速い。なお切り分けで条件を緩めた状態は本番環境として危険なため、
原因特定後ただちに厳密な条件へ戻している。
